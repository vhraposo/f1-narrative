# V4.0 — AI Behavior Foundation (Architecture)

## Objetivo

Criar o contrato central de comportamento do Universe: um read model determinístico
(`BehaviorContext`), um contrato de entrada (`BehaviorDecisionRequest`), candidatos de ação
(`BehaviorCandidate`), uma policy determinística (`BehaviorPolicy`) e auditoria em `AiDecision`.
Nenhum LLM é necessário; nenhuma autonomia é executada nesta fase.

## Auditoria (o que já existia)

| Conceito | Entidade/serviço existente | Uso no V4.0 |
| --- | --- | --- |
| Decisão AI | `AiDecision` (status, actionType, reason, contextVersion, policyCode, metadata, conversationId, executedMessageId/EventId) | Reutilizada; candidates/selected/policy/fingerprint/trigger no `metadata` |
| Personagem | `Character` (+ `controlledBy`, `dna`, `biography`) | IDENTITY/CURRENT_STATE |
| Personalidade | `CharacterPersona` + `PersonaTrait.context` (ON_TRACK/OFF_TRACK) | PERSONALITY consome apenas ON_TRACK |
| Experiência | `PilotExperience` (status, salience, source/sourceKey, revision) | EXPERIENCE |
| Memória | `Memory` + `MemoryCharacter` (importance, status, derivation) | MEMORY |
| Relações | `Relationship.dimensions` (JSON) | RELATIONSHIPS |
| Mundo | `WorldState` (currentDate/Season/Race/Session) | WORLD; fonte de verdade temporal |
| Eventos | `Event`/`EventCharacter` (narrativo) e `TimelineEvent` (canônico) | CURRENT_STATE (evento do trigger) |
| Conversa | `Conversation`/`ConversationParticipant`/`Message` | CONVERSATION |
| Disponibilidade/agenda | `CharacterAvailability`, `CharacterSchedule` | AVAILABILITY/SCHEDULE |
| Notícias | `NewsItem` | NEWS |
| Esporte | `DriverProfile`, `ChampionshipStanding`, `RaceResult` | MOTORSPORT (leitura) |

Conclusão: nenhuma entidade nova de domínio é necessária. A única mudança de schema é aditiva
(`AiActionType` ganha `RESPOND`, `CREATE_MEMORY`, `UPDATE_RELATIONSHIP`).

## Contratos

- `BehaviorTrigger`: `MESSAGE_RECEIVED`, `EVENT_CREATED`, `RACE_SESSION_COMPLETED`, `RACE_FINISHED`,
  `RELATIONSHIP_CHANGED`, `MEMORY_CREATED`, `SCHEDULE_DUE`, `WORLD_ADVANCED`, `USER_REQUESTED`,
  `AUTONOMOUS_TICK`.
- `BehaviorActionType`: `NO_ACTION`, `RESPOND`, `SEND_MESSAGE`, `CREATE_EVENT`, `CREATE_MEMORY`,
  `UPDATE_RELATIONSHIP` (propostas; execução é V4.1+ via commands).
- `BehaviorDecisionRequest`: universeId, characterId, trigger, worldDate (explícito), conversationId?,
  eventId?, raceId?, session?, userInitiated, metadata.
- `BehaviorCandidate`: id determinístico (`cand:<action>:<target|self>`), actionType, priority,
  reasonCode, requiredContext, targetCharacterId, conversationId, preconditions,
  failedPreconditions, consequencesPreview, metadata.
- `BehaviorPolicyResult`: policyCode (`behavior-policy.v1`), candidates, selected, rejected.

## BehaviorContext

Read model em `behavior.context.ts`, somente leitura, com seções IDENTITY, PERSONALITY,
CURRENT_STATE, GOALS (vazia — V4.1), MEMORY, EXPERIENCE, RELATIONSHIPS, WORLD, MOTORSPORT,
CONVERSATION, AVAILABILITY, SCHEDULE, NEWS; além de `version` (`behavior-context.v1:<hash16>`),
`fingerprint` (SHA-256 canônico das seções), `assembledAt` (= worldDate) e `omitted/reasons`.
Validação: personagem inexistente → 404; universo divergente → 403; conversa/evento/corrida
inexistentes quando referenciados → 404. Nenhuma escrita, nenhum provider, nenhum LLM.

## Policy determinística

Prioridades fixas: RESPOND 90 > SEND_MESSAGE 70 > CREATE_MEMORY 60 > UPDATE_RELATIONSHIP 50 >
CREATE_EVENT 40 > NO_ACTION 0. Seleção por (prioridade desc, ordem de ação, id) após avaliar
preconditions (`CONTROLLER_IS_AI`, `CHARACTER_IS_PARTICIPANT`, `AVAILABILITY_OPEN`,
`RELATIONSHIP_TARGET_PRESENT`, `SIGNIFICANT_EXPERIENCE_PRESENT`, `ACTIVE_SEASON_PRESENT`).
Caracteres `USER` nunca agem autonomamente (`CONTROLLER_IS_AI` falha quando a ação não é
`USER_REQUESTED`/`userInitiated`). Candidatos rejeitados permanecem no audit com o motivo.
Sem `Math.random` e sem `Date.now`: o tempo vem de `worldDate`.

## Decision Engine × Language Engine

- Decision Engine: determinístico, decide a ação e persiste `AiDecision` (status `DECIDED` ou
  `NO_ACTION`; `REJECTED` reservado a fluxos com execução). `llmUsed: false`.
- Language Engine: interface opcional (`BehaviorLanguageEngine`); `createDeterministicLanguageEngine`
  transforma ação aprovada em texto sem LLM. A geração real via provider entra na V4.2.

## Auditoria

`AiDecision.metadata` registra: trigger, worldDate, userInitiated, fingerprint do contexto, engine,
llmUsed, candidates, selected, rejected, contextOmissions e requestMetadata sanitizado
(chaves sensíveis → `[REDACTED]`). Nenhum secret/API key é persistido.

## XState — avaliação

Avaliado e **não adotado na V4.0**: a policy é uma função pura sobre um read model; não há estados
concorrentes nem atores a orquestrar. Adicionar XState agora criaria dependência sem valor e risco de
virar fonte de verdade paralela. A adoção será reavaliada em V4.2/V4.7 (turnos multi-ator e jobs),
sempre com o banco como source of truth. Decisão registrada para revisão.

## Providers / modelos

Nenhum provider é usado nesta fase. Contrato de Language Engine preparado para receber o provider
existente (Ollama) e OpenAI Responses API (Structured Outputs + Function Calling) nas fases de
conversa, com modelo configurável (sem hardcode).

## Invariantes

- LLM não escreve estado canônico (nenhum LLM nesta fase).
- Nenhum comando de execução; ações são apenas propostas auditadas.
- Isolamento por Universe e por controller (USER nunca age autonomamente).
- `worldDate` explícito → determinismo total; mesma entrada = mesma saída.
- Contexto não contém OFF_TRACK, goals (V4.1), nem dados de outro Universe.

## Limitações

- GOALS ainda vazio (V4.1) e sem derivadores.
- Cooldowns/fingerprints de ação (V4.1) e commands de execução (V4.1) não existem.
- NEWS não é escopada por Universe (`NewsItem` não possui `universeId`).
- Nenhuma rota/UI nesta fase (Behavior Inspector é V4.8); uso é via service.
