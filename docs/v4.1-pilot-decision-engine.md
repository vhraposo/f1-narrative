# V4.1 — Pilot Decision Engine

## Objetivo

Dar ao piloto objetivos persistentes e a capacidade de escolher uma ação válida, com execução
determinística por Command Layer e auditoria completa — sem LLM e sem XState.

Fluxo: `BehaviorContext → Goals → Policy → Candidates → Score → Select → Command → Domain Validation → Persist → Audit`.

## Arquitetura anterior (V4.0)

BehaviorContext (read model determinístico), BehaviorPolicy (candidatos + prioridade fixa),
BehaviorDecision (persiste `AiDecision`), Language Engine determinístico. Sem goals, sem cooldown,
sem fingerprints de ação, sem execução.

Auditoria prévia: já existiam `AiDecision`, `Character`, `DriverProfile`, `CharacterPersona`,
`PilotExperience`, `Memory`, `Relationship`, `Event`, `Conversation`/`Message`,
`CharacterAvailability`, `CharacterSchedule`, `WorldState`, `TimelineEvent` e a camada legada
`ai-behavior` (executeCharacterDecision com provider/LLM). Nenhum modelo de Goal existia.
Decisão: criar `CharacterGoal`; **não** duplicar writers — commands reutilizam
`createEventWithDerivations` e `canonicalizeRelationshipPair`, e escrevem Message/Memory com as
mesmas validações dos serviços existentes.

## CharacterGoal

Campos: `universeId`, `characterId`, `kind`, `priority`, `status`, `source`, `ruleCode`,
`fingerprint`, `targetCharacterId`, `targetRaceId`, `seasonId`, `validFrom`, `validTo`, `progress`,
`metadata`, `completedAt`. Unique `(universeId, fingerprint)`; índices por
`(universeId, characterId, status)`, `(characterId, status)`, `(universeId, kind, status)` e `validTo`.

Enums: `CharacterGoalKind` (11 tipos), `CharacterGoalStatus` (ACTIVE/PAUSED/COMPLETED/FAILED/EXPIRED/CANCELLED),
`CharacterGoalSource` (SYSTEM/MANUAL/DERIVED).

## Derivação (ruleCodes)

| Regra | Condição | Goal | Prioridade |
| --- | --- | --- | --- |
| `goal-rule.race-win.v1` | AI + corrida corrente não FINISHED | WIN_RACE | 100 |
| `goal-rule.championship-challenge.v1` | AI + standing ≤ 3 | WIN_CHAMPIONSHIP | 90 |
| `goal-rule.recover-after-setback.v1` | experience SPORTING_DEFEAT/CONFLICT HIGH+ | RECOVER_AFTER_SETBACK (validTo +7d) | 80 |
| `goal-rule.teammate-performance.v1` | posição pior que o teammate | OUTPERFORM_TEAMMATE (target teammate) | 70 |
| `goal-rule.confront-rival.v1` | rivalry ≥ 0.7 + setback | CONFRONT_RIVAL (target rival) | 65 |
| `goal-rule.protect-relationship.v1` | rivalry ≥ 0.5 | PROTECT_RELATIONSHIP (target rival) | 55 |

Inputs proibidos: OFF_TRACK personality, biography como regra, interesses/projetos, LLM, conhecimento
externo. `resolveCharacterGoals` é leitura pura (goals persistidos + derivados sintéticos);
`reconcileCharacterGoals` persiste (idempotente por fingerprint).

## Reconcile, completion e expiração

- Completion determinística: WIN_RACE (corrida FINISHED + P1), WIN_CHAMPIONSHIP (season FINISHED +
  posição 1), OUTPERFORM_TEAMMATE (posição melhor que o teammate), RECOVER_AFTER_SETBACK (sem
  setback ativo). Falha: WIN_RACE/WIN_CHAMPIONSHIP encerrados sem o resultado → FAILED.
- Expiração: `validTo < worldDate` ou derivação que deixou de valer (EXPIRED). Goals terminais não
  são reprocessados (terminalIds evita sobrescrita por expiração no mesmo ciclo).
- MANUAL prevalece: derivação conflitante não é criada e o conflito é contado (`manualConflicts`).

## Scoring (behavior-scoring.v1)

`scoreBehaviorCandidate` retorna breakdown explícito:
goalAlignment (até 40, alinhamento por goal ponderado pela prioridade), triggerRelevance (30),
contextRelevance (10), relationshipRelevance (5), experienceRelevance (5), availabilityBonus (5),
cooldownPenalty (-100), duplicatePenalty (-100), policyBonus (10 × prioridade/90).
Seleção final: candidato válido (sem preconditions falhas) → score desc → prioridade desc → ordem
de ação → id. Nenhum random/Date.now: o tempo vem de `worldDate`.

## Cooldown e action fingerprint

- `actionFingerprint` = SHA-256 de `{universeId, characterId, actionType, target, conversationId,
  eventId, goalIds ordenados, worldDateBucket, contextFingerprint, policyVersion}`.
- `worldDateBucket` = dia UTC de `worldDate`. Cooldown consulta `AiDecision` EXECUTED do character
  (últimos 200): chaves `${actionType}:${target}:${bucket}` e fingerprints executados.
- Preconditions `COOLDOWN_CLEAR` (SEND_MESSAGE) e `NO_DUPLICATE_ACTION` (todas as ações executáveis)
  rejeitam repetição no mesmo bucket/fingerprint. Sem tabela de cooldown (audit em AiDecision).

## Command Layer

`behavior.commands.ts` com validate/authorize/execute por ação, sempre dentro de transação:
- RESPOND/SEND_MESSAGE: conversa existe, personagem é participante, AI (ou user-initiated),
  alvo no mesmo Universe; cria `Message` com texto do language engine determinístico.
- CREATE_EVENT: apenas SOCIAL/PERSONAL/RELATIONSHIP, via `createEventWithDerivations`.
- CREATE_MEMORY: `derivation: RULE_DERIVED`, `derivedKey = actionFingerprint`, participants
  validados, universeId explícito.
- UPDATE_RELATIONSHIP: par canônico, delta determinístico (respect/rivalry ±) com clamp [-100,100].
Códigos estáveis: CHARACTER_NOT_AI, TARGET_NOT_FOUND, TARGET_NOT_PARTICIPANT, UNIVERSE_MISMATCH,
COMMAND_NOT_ALLOWED, PRECONDITION_FAILED, EXECUTION_FAILED.

## Execução, stale e idempotência

`executeBehaviorDecision`: carrega a decisão; se EXECUTED → ALREADY_EXECUTED; rebuild do contexto a
partir de `metadata.requestPayload`; se o fingerprint atual difere do armazenado → `REJECTED`
STALE_CONTEXT; transação com advisory lock por character; revalidação de estado e de fingerprint
duplicado (`ACTION_DUPLICATE`); EXECUTING → command → EXECUTED com `executedMessageId`/
`executedEventId` e `metadata.execution` (command, fingerprint, latencyMs). Erros de domínio →
REJECTED; erros inesperados → FAILED. Reexecutar a mesma decisão é idempotente.

## API (mínima)

- `GET /api/behavior/goals?characterId=`
- `POST /api/behavior/goals` (MANUAL, owner-scoped)
- `PATCH /api/behavior/goals/:goalId` (status/prioridade)
- `POST /api/behavior/decisions` (avalia; worldDate padrão = WorldState.currentDate)
- `GET /api/behavior/decisions/:decisionId`
- `POST /api/behavior/decisions/:decisionId/execute`

Ownership via Universe/usuário; cross-universe retorna 404/403 conforme convenção existente.

## Segurança e invariantes

- LLM não participa; nenhum provider é necessário.
- USER nunca age autonomamente (CONTROLLER_IS_AI falha fora de USER_REQUESTED/userInitiated).
- Command é a fronteira final: revalida universo/participação/controller no momento da execução.
- RaceResult, ChampionshipStanding, TimelineEvent, WorldState e SeasonDriverEntry nunca são
  alterados pelo behavior engine (apenas leitura).
- Metadata de decisão é sanitizada (chaves sensíveis → `[REDACTED]`); sem prompt/LLM.

## Limitações

- Cooldown por bucket diário (granularidade maior fica para V4.2/V4.7).
- Sem turn budget de conversa (V4.2); sem relação social completa (V4.3); memória rica (V4.4).
- `resolveCharacterGoals` sintetiza derivados não persistidos quando chamado fora do fluxo de decisão.
- XState segue não adotado (reavaliar V4.2/V4.7).
