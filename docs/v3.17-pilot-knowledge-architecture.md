# V3.17 — Pilot Knowledge, Persona & Context: Arquitetura

> **Status:** implementado (V3.17 concluída). Base auditada: HEAD `2e7b7ba` (branch `V3-NewFeats`), V3.15/V3.16 concluídas.
> **Princípio central:** *External Knowledge ≠ Universe Truth*. A camada externa é baseline pública; o Universe sempre vence.

---

## 1. Objetivo

Permitir que o LLM responda como um piloto de forma consistente com identidade, biografia, personalidade pública, estilo de comunicação, interesses, relacionamentos, histórico, memórias do Universe e estado atual — via uma camada de conhecimento externo estruturada e um `PilotContextResolver` determinístico e limitado, integrado à geração existente sem quebrar V3.14/V3.15/V3.16.

Camadas (sem colapsar em um JSON único):

```
External Driver Knowledge  (baseline pública, mirror-keyed)
        ↓
Universe Driver/Character  (overrides: Character.biography, CharacterPersona, UniverseDriverRelationship, Memory, Timeline)
        ↓
Pilot Context Resolver     (merge efetivo, determinístico, limitado)
        ↓
Generation                 (seção opcional PILOT_CONTEXT, speaker-only)
```

## 3. Modelo de dados (migration nova, aplicada somente no TEST durante o desenvolvimento)

Nova migration `add_pilot_knowledge_foundation`. Nenhuma tabela existente é alterada. Nomes de enums são novos e exclusivos.

### 3.1 Source ledger

- **`ExternalKnowledgeSource`** — ledger de proveniência/licença (≠ RAG `ExternalSource`):
  `provider` (`ExternalKnowledgeProvider`: `F1DB|WIKIDATA|F1_OFFICIAL|FIA_OFFICIAL|TEAM_OFFICIAL|DRIVER_OFFICIAL|REPUTABLE_NEWS|CURATED`), `sourceKind` (`ExternalKnowledgeSourceKind`), `url?`, `title?`, `license` (`ExternalKnowledgeLicense`: `CC_BY_4_0|CC0|CC_BY_SA_4_0|PROPRIETARY_REFERENCE_ONLY|UNKNOWN`), `attributionRequirement?`, `attributionText?`, `publishedAt?`, `retrievedAt @default(now())`, `sourceVersion?`, `metadata Json?`. Índices `[provider, retrievedAt]`; `@@unique([provider, url])` (urls nulos não colidem).
  Nunca guarda página/artigo/transcrição — apenas metadados + claims derivados.

### 3.2 Identidade e biografia

- **`ExternalDriverProfile`** — 1:1 com `ExternalDriver`:
  `externalDriverId @unique`, `fullName?`, `publicName?`, `dateOfBirth?`, `placeOfBirth?`, `nationality?`, `representedCountry?`, `driverNumber Int?`, `driverCode?`, `currentTeamName?`, `officialLinks Json?`, `biographyDisplay?`, `biographyContext?`, `biographySourceId? → ExternalKnowledgeSource (SetNull)`, `wikidataQid? @unique`, `f1dbDriverId? @unique`, `refreshStatus` (`ExternalRefreshStatus`: `FRESH|STALE|UNKNOWN`), `lastVerifiedAt?`, `sourceId?`, timestamps.
  Sem residência/telefone/email/medicina — política de privacidade (§9).

### 3.3 Persona pública externa

- **`ExternalDriverPersona`** — 1:1 com `ExternalDriverProfile`: `schemaVersion "external-persona.v1"`, `summary?`, `status` (`ExternalClaimStatus`: `SUPPORTED|UNCERTAIN|CONFLICT|UNKNOWN`), `lastVerifiedAt?`.
- **`ExternalPersonaTrait`** — `personaId`, `traitKey`, `value`, `sourceKind` (`ExternalPublicTraitSource`: `DIRECT_SELF_DESCRIPTION|OBSERVED_PUBLIC_BEHAVIOR|INFERRED`), `status` (`ExternalClaimStatus`), `confidence Float?` (interno; nunca no prompt), `evidenceId? → ExternalPersonaEvidence (SetNull)`, `@@unique([personaId, traitKey])`.
- **`ExternalPersonaEvidence`** — `personaId`, `traitKey`, `proposedValue`, `evidenceType` (`ExternalPublicEvidenceType`: `SELF_DESCRIPTION|OFFICIAL_INTERVIEW|FIA_TRANSCRIPT|TEAM_PROFILE|F1_PROFILE|DRIVER_OFFICIAL|REPUTABLE_NEWS|STRUCTURED_DATA`), `sourceId? → ExternalKnowledgeSource`, `summary` (síntese original ≤500, nunca o texto bruto), `confidence Float?`, `status ExternalClaimStatus @default(SUPPORTED)`, `retrievedAt @default(now())`.

Registry de traits públicos (grupos COMMUNICATION/BEHAVIOR/INTERESTS/MOTIVATIONS/SPEECH) com label, prioridade e caps vive em `pilot-knowledge.policy.ts`. Valores são strings descritivas ("frequentemente direto e conciso"), nunca scores psicológicos.

### 3.4 Relacionamentos

- **`ExternalDriverRelationship`** — `externalDriverId`, `kind` (`DriverRelationshipKind`: `ROMANTIC_PARTNER|SPOUSE|PARENT|CHILD|SIBLING|TEAMMATE|TEAM_RELATION|MENTOR|OTHER_PUBLIC_RELATION`), `targetType` (`DriverRelationshipTarget`: `DRIVER|PUBLIC_PERSON`), `targetExternalDriverId? → ExternalDriver (SetNull)`, `targetWikidataQid?`, `displayName`, `state` (`DriverRelationshipState`: `ACTIVE|ENDED|UNKNOWN`), `validFrom?`, `validTo?`, `sourceId?`, `confidence Float?`, `lastVerifiedAt?`. Múltiplas linhas por alvo/fonte são permitidas (conflito é dado, não erro). Rivalidade nunca é inferida.
- **`UniverseDriverRelationship`** (override do Universe; camada separada) — `universeId`, `characterId → Character`, `kind`, `targetType`, `targetCharacterId? → Character (SetNull)`, `targetWikidataQid?`, `displayName`, `state`, `validFrom?`, `validTo?`, `createdById? → User (SetNull)`, timestamps. Universo A nunca toca B. `Relationship` (Character↔Character, dimensions) permanece intocado.

### 3.5 Eventos históricos

- **`ExternalDriverEvent`** — `externalDriverId`, `category` (`ExternalDriverEventCategory`: `F1_DEBUT|FIRST_POINT|FIRST_PODIUM|FIRST_POLE|FIRST_WIN|FIRST_CHAMPIONSHIP|CHAMPIONSHIP|TEAM_CHANGE|MAJOR_CAREER_MILESTONE|SIGNIFICANT_RACE|CAREER_ENTRY`), `title`, `eventDate?`, `seasonYear?`, `externalRaceId? → ExternalRace (SetNull)`, `summary?`, `importance Int @default(3)`, `derivation` (`ExternalEventDerivation`: `DERIVED_RESULTS|DERIVED_STANDINGS|CURATED_SOURCE`), `sourceId?`, `dedupeKey`, `@@unique([externalDriverId, dedupeKey])`.
  Marcos determinísticos são derivados dos dados esportivos externos (nunca via LLM); `ExternalDriverEvent` é resumo/marco e **não duplica** `RaceResult`.

### 3.6 Universe override de biografia

Sem coluna nova: `Character.biography` é o override Universe-scoped da biografia; efetiva = `Character.biography ?? ExternalDriverProfile.biographyDisplay`. Documentado em D-067 (evita campo redundante).

## 4. Providers

Interfaces (`providers/provider.types.ts`):

```
ExternalDriverKnowledgeProvider {
  source: ExternalKnowledgeProvider;
  resolveDriverIdentity(query): ProviderIdentityMatch[];   // candidatos + evidências de match
  fetchStructuredProfile(identity): StructuredDriverProfile;
  fetchRelationships(identity): ProviderRelationship[];
  fetchCareerData(identity): ProviderCareerData;           // seasons/teams/results agregados
  fetchSourceReferences(identity): ProviderSourceReference[];
}
```

- **F1DB provider** (`providers/f1db.provider.ts`): lê um release estruturado (JSON) de um diretório local configurado (`F1DB_DATA_DIR`); sem HTML; `sourceVersion` = release tag; licença `CC_BY_4_0` com attribution. Nenhuma dependência de rede em runtime/testes.
- **Wikidata provider** (`providers/wikidata.provider.ts`): SPARQL (`WIKIDATA_SPARQL_URL`, default `https://query.wikidata.org/sparql`) para data/local de nascimento, nacionalidade, spouse/unmarried partner, relações familiares públicas, identifiers e sites oficiais; persiste `wikidataQid`. Live/opt-in (admin refresh); testes usam fixtures gravados/sanitizados com `fetchImpl` injetado.
- **Primary source enrichment** (`providers/primary-source.ingest.ts`): registra `ExternalKnowledgeSource` + claim derivado a partir de metadados fornecidos (URL/título/publishedAt/sourceKind/licença `PROPRIETARY_REFERENCE_ONLY`); **não** busca páginas automaticamente e **não** persiste conteúdo. `fetch → extract → discard raw` é permitido apenas via operandor/admin com provider de extração explícito.
- Jolpica/OpenF1 permanecem como estão; V3.17 não adiciona dependência nova deles para Persona.

**Identity resolution** (`pilot-knowledge.identity.ts`): candidatos por `wikidataQid`/`f1dbDriverId`/`(source, externalId)`; fallback por nome normalizado + nacionalidade/numero com limiar; ≥2 candidatos incompatíveis → `AMBIGUOUS_IDENTITY` (nunca chute); 0 candidatos + F1DB → provisiona `ExternalDriver` com `source="f1db"` e `externalId` estável. Casos de teste: Max, Lando, Sainz/Sainz Jr. (colisão), histórico, inexistente. *(V3.20.1: `pilot-knowledge.provision.ts` adiciona provisionamento lazy e idempotente a partir do espelho interno — identidade/biografia/marcos ao abrir o piloto; providers externos seguem opt-in.)*

## 5. Pipeline de extração (LLM apenas como extrator)

```
Source (metadados + claims estruturados)
    ↓
Extractor (interface; implementação provider-backed opcional / determinística nos testes)
    ↓ SUPPORTED | UNSUPPORTED | UNCERTAIN + claims com evidence references
Validação contra a fonte (claim precisa de referência)
    ↓
Evidence (ExternalPersonaEvidence) + Source (ExternalKnowledgeSource)
    ↓
Resolução (autoridade → temporalidade → conflito)
    ↓
ExternalDriverPersona / ExternalDriverRelationship / ExternalDriverProfile
```

- O extractor tem prompt próprio ("extraia claims públicos suportados…") e devolve JSON validado por zod; nunca "imagine a personalidade".
- `INFERRED` exige ≥2 evidências independentes; caso contrário `UNCERTAIN` (não apresentado como certeza).
- Conflito material permanece `CONFLICT` (valor adotado pela autoridade + registro do conflito).
- Nenhuma inferência de doença/estado mental/diagnóstico/fitness/motivos privados.

## 6. Pilot Context Resolver

`apps/api/src/modules/pilot-context/pilot-context.resolver.ts`:

```
resolvePilotContext(db, { universeId, speakerCharacterId, topic? (string), worldDate? })
→ {
    sections: {
      identity, biography, effectivePersona, relationships,
      historicalContext, memories, currentUniverseState, conversationContext
    },
    origin: { biography: UNIVERSE|EXTERNAL|NONE, personaTraits: per-key universe|external },
    omitted: { reasons: string[] },
    fingerprint: sha256 derivado dos inputs (determinístico)
  }
```

- **Speaker-only**: só o `speakerCharacterId`; zero consulta de persona/relacionamentos de terceiros.
- **Queries agrupadas**: 1 query por tipo (profile+persona+traits, relationships, events, memories, world/state), sem N+1.
- **Precedência**: universe state → universe relationships → universe persona (CharacterPersona) → external relationships → external persona → external biography → external history → memories → conversa.
- **Relevância**: `topic` (ex.: "Mônaco", "2025", piloto/time mencionado) filtra eventos/memórias deterministicamente; sem relação → milestones recentes/importantes.
- **Caps** (constantes nomeadas em `pilot-context.policy.ts`, testáveis): biografia de contexto ≤600, traits ≤12, relacionamentos ≤8, eventos ≤8, memórias ≤6, texto total ≤2000; truncamento registra reason.
- **Nunca retorna**: evidence raw, source metadata, confidence, IDs internos — apenas texto resolvido.

**Biografia efetiva** = `Character.biography` (override) ?? `ExternalDriverProfile.biographyContext` (externo), com `origin` para UI.
**Persona efetiva** = merge por `traitKey` (CharacterPersona vence; traits só-externos entram), com labels públicos.
**Relacionamentos** = override do Universe quando existir; senão resolução externa (autoridade → temporalidade); classificação de leitura `MATCH|DIVERGENT|UNKNOWN|CONFLICT` calculada quando comparando override × externo.

## 7. Integração com geração

- Nova seção **opcional `PILOT_CONTEXT`**, emitida entre `CHARACTER_DNA` e `WORLD_STATE`, **somente** quando o speaker possui pilot context resolvido (piloto com binding externo/conhecimento).
- `composeSystemPrompt(..., speakerPilotContextText?)` — assinatura aditiva; `SECTION_IDS` e `assertGenerationContract` aceitam a seção como opcional.
- Conteúdo: identidade, biografia (origem rotulada de forma neutra), persona efetiva, relacionamentos relevantes, histórico relevante, memórias relevantes, estado atual compacto. Sem confidence/source metadata/IDs.
- `loadSpeakerPilotContext(db, speakerCharacterId)` faz 1 chamada agrupada e degrada para `null` (seção omitida) quando: sem `DriverProfile`, sem binding, sem conhecimento externo e sem override; ou quando o módulo está indisponível (ambiente sem migration) — nunca quebra a geração.
- `generationKey` inalterado no mecanismo: o texto entra em `systemPrompt`, então perfil/persona/relacionamento/eventos/memória/estado alteram a chave automaticamente; fingerprint do resolver é determinístico e testável à parte.
- Preservados: SSE, NullProvider, speaker-only, `CURRENT_TURN`, RAG, research, AI Behavior, projection.

## 8. Refresh, conflito e manutenção

- **Refresh, conflito e manutenção:** refresh reutiliza `ExternalSyncRun` com scopes `DRIVER_PROFILE`, `DRIVER_RELATIONSHIPS`, `DRIVER_EVENTS` — traits de persona não têm run próprio (entram por ingestão de evidência explícita; deviação documentada em §14).
- Fluxo: external → atualiza ExternalDriverKnowledge → resolver → visão efetiva. Nunca: refresh → CharacterPersona / Relationship / Timeline / Memory.
- Endpoints (módulo `pilot-knowledge`):
  - `GET /api/pilot-knowledge/drivers/:characterId` — visão agregada (owner-only, leak-safe 404).
  - `POST /api/pilot-knowledge/drivers/:characterId/refresh` — ADMIN; providers injetados; sem providers → `503 PROVIDERS_UNAVAILABLE`.
  - `GET /api/pilot-knowledge/status` — ADMIN; contagens de refresh/stale/conflict (bounded).
  - `POST/PATCH/DELETE .../relationships` — CRUD do override Universe (owner).
- UI de manutenção (quando ADMIN): refresh, conflitos, stale, detalhes de fonte — sem acesso ao usuário comum.

## 9. Privacidade, licenças e factuality

- Somente informação pública relevante. Proibido: residência, telefone, email privado, localização em tempo real, documentos, dados bancários/médicos, conversas privadas, vazamentos, dados de menores além do estritamente público. Relacionamentos: contextual e respeitoso.
- Licenças como metadata por source/claim: F1DB `CC BY 4.0` (attribution), Wikidata `CC0`, Wikimedia `CC BY-SA 4.0`, primary commercial `PROPRIETARY_REFERENCE_ONLY`. Nada de "web page = free data"; sem crawler; sem páginas/artigos/transcripts persistidos; somente facts/claims/summaries originais/metadados.
- Chat: nunca inventar fatos/relacionamentos/filhos/hobbies/citações/diagnósticos; ausência de dado permanece ausência ("Não tenho informação pública confiável sobre isso."); persona orienta estilo, nunca voice cloning ou coleção de frases.
- Currentness: toda claim relevante tem `retrievedAt`/`lastVerifiedAt` (e `validFrom/validTo` quando aplicável); `validTo = null` significa "sem data final conhecida", não verdade eterna; UI mostra data de verificação.
- Autoridade: `PRIMARY_OFFICIAL > STRUCTURED_LICENSED > REPUTABLE_SECONDARY > OTHER_SECONDARY`; temporalidade resolve por validade; conflito do mesmo período permanece `CONFLICT`.

## 10. Compatibilidade V3.14/V3.15/V3.16

- `CharacterPersona` continua sendo a persona Universe/Character (override/personalização); a camada externa é separada e nunca a substitui (V3.14 preservada). Promoção de trait externo para `CharacterPersona` só via `PersonaEvidence` + review ADMIN (sem bypass, sem escrita automática).
- `Memory` continua Universe-only; todo histórico externo é `ExternalDriverEvent`, nunca Memory.
- Timeline/corrections são a verdade esportiva do Universe; o resolver lê o estado atual (correções aplicadas visíveis); nenhuma regeneração automática de Persona/Memory/Evolution nesta fase.
- Nenhum segundo sistema temporal/correction; nenhuma alteração de `Relationship` existente.
