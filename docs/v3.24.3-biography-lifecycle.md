# V3.24.3 — Biography Lifecycle (Cache-First, Generation Runs & Backfill)

## Problema

Abrir um piloto disparava provisionamento/generation no `GET /api/pilot-knowledge/drivers/:characterId`
(`ensurePilotKnowledgeProvisioned` dentro da leitura). Isso tornava a leitura cara, não auditável e
sem controle de concorrência, com risco de variar o texto entre aberturas.

## Modelo

- Leitura (`GET`) é **pura**: monta a view a partir do que já está persistido + `readBiographyState`.
- Geração acontece apenas por comando explícito: `POST .../biography/generation` (usuário dono) ou
  `POST /api/pilot-knowledge/biography/backfill` (ADMIN). A UI dispara o POST quando o estado é
  `MISSING`/`STALE` — nunca o GET.
- Toda execução é registrada em `BiographyGenerationRun` (migration
  `20261001120000_add_biography_generation_run_and_trait_context`).

## Estados de lifecycle

`MISSING`, `READY`, `READY_FALLBACK`, `STALE`, `GENERATING`, `FAILED`.

- `READY`: display persistido; `STALE` quando `generatorVersion` difere de `biography-composer.v3`
  ou `evidenceVersion` difere da curadoria atual.
- `GENERATING`: existe run ativo (`PENDING`/`RUNNING`).
- Bio do Universe (edição manual) é `READY` com `origin: UNIVERSE` e nunca é sobrescrita.

## Run persistido (auditoria)

`BiographyGenerationRun`: `status`, `mode` (`LLM` | `RICH_DETERMINISTIC` | `COMPACT_FALLBACK`),
`provider`, `model`, `prompt` (JSON sanitizado), `promptHash` (SHA-256), `promptVersion`,
`evidenceVersion`, `generatorVersion`, `fingerprint`, `fallbackReason`, `failureReason`,
`outputSourceId`, `timings`, `startedAt`/`completedAt`.

- `sanitizePromptPayload` redige `sk-…`, `Bearer …`, `api_key`, `authorization` antes de persistir.
- `promptHash` = SHA-256 de `{ systemPrompt, userPrompt }` (auditoria do que foi enviado ao provider).

## Cache-first e single-flight

- `requestBiographyGeneration` reutiliza run terminal quando o estado já é `READY`/`READY_FALLBACK`
  e `evidenceVersion` do último run == estado atual → `{ reused: true, skipped: true }`, sem novo run.
- Concorrência no mesmo personagem é serializada por uma fila in-process; ao entrar, re-checa run ativo.
- Backfill é sequencial, idempotente e reporta `targets/succeeded/fallback/failed/skipped/rich`.

## Rotas

- `GET /api/pilot-knowledge/drivers/:characterId` → `{ pilot, biographyStatus, sync }` (leitura pura;
  `sync.provisioned` sempre `false`).
- `POST .../biography/generation` → `202 { generation: { runId, status, reused, skipped? } }`.
- `GET .../biography/generation` → último run (para polling).
- `POST /api/pilot-knowledge/biography/backfill` → `{ backfill }` (403 para não-admin).

## UI (Web)

- Ao abrir: `MISSING` mostra skeleton na área da Biografia e toast persistente "Preparando biografia…";
  `STALE` mantém o texto antigo + toast "Atualizando biografia…".
- Polling curto do run (1,5 s) até estado terminal; toast vira sucesso/erro (dedupe por run pendente).
- `GENERATING` mostra indicador "Atualizando biografia…" no card; leitura nunca gera.

## Validação real (DEV)

- Backfill: 46 alvos (2 universes × 23), **23/23 perfis com display persistido**, 6 rich
  (Gasly, Norris, Max × 2 universes), 40 compactos factuais, 0 falhas.
- Max: `READY`, 8 parágrafos, 3.790 caracteres; segunda solicitação reutilizou o mesmo run
  (runs 1 → 1, `skipped: true`); backfill re-executado: 46/46 `skipped`, 0 falhas.
- Backup: `f1narrative_dev_pre_v3243.dump`; DEV migrado de 37 → 38 migrations.

## Testes

- `biography.lifecycle.test.ts` (6): prompt persistido/hash, READY leitura pura, STALE, single-flight,
  backfill + proteção do Universe, sanitização.
- Rotas 9/10 reescritas (cache-first, generation antes de editar).

## Decisões

- D-097 — GET é leitura pura; geração só sob comando.
- D-098 — Toda geração registrada com prompt sanitizado, hash e fingerprint; single-flight por personagem.
