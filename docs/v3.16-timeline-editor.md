## 1. Objetivo

Permitir que o dono do Universe edite visualmente um acontecimento histórico sem conhecer comandos nem IDs internos, com o fluxo obrigatório:

1. abrir o evento na Linha do Tempo;
2. escolher **Editar** (habilitado apenas quando o edit model permite);
3. preencher o formulário do kind;
4. **Pré-visualizar correção** (nunca aplica direto);
5. revisar **ANTES/DEPOIS** e **IMPACTOS** (classificação, campeão, `#1`, narrativa);
6. confirmar explicitamente;
7. aplicar — com tratamento de `409 PREVIEW_STALE` (nova pré-visualização obrigatória).

O histórico anterior nunca é alterado: o evento antigo permanece e a correção é um novo evento com `supersedesId`.

## 2. Edit model (V3.16.1)

`buildTimelineEventEditModel(universeId, item)` monta, a partir do evento (`apps/api/src/modules/timeline/timeline.editor.ts`):

| Campo | Papel |
|---|---|
| `editorKind` | `RACE_RESULT \| SPRINT \| NUMBER \| STANDING \| RACE \| null` (preservado mesmo quando bloqueado, para a UI explicar) |
| `canEdit` | `false` quando `blockedReason` está presente |
| `blockedReason` | `NO_VISUAL_EDITOR`, `EVOLUTION_STALE`, `DERIVED_STANDING`, `RESULT_NOT_FOUND`, `DRIVER_NOT_IN_SEASON`, `RACE_NOT_FOUND`, `SEASON_NOT_FOUND`, `WORLD_STATE_MISSING` |
| `defaultWorldDate` | `world.currentDate` (ISO) — a correção nunca é agendada no futuro |
| `suggestedSupersedesId` | evento atual, para os kinds corrigíveis (inclui `RACE_UPDATED`); `null` para `RACE_SCHEDULED` etc. |
| `values` / `currentValues` | pré-preenchimento do formulário e estado atual efetivo (SPRINT inclui `neutralizedStart` 1/0/null e `distancePct` de `metadata.eligibility`) |
| `narrativeStaleEventIds` | registros de narrativa ligados ao alvo |

Regras de bloqueio reutilizam as decisões congeladas da V3.15: evolução cumulativa → `EVOLUTION_STALE`; standing derivado de resultados (`DERIVED_STANDING`) permanece correção de origem esportiva; `NO_VISUAL_EDITOR` para kinds sem formulário.

## 3. Formulários por kind (V3.16.2)

| `editorKind` | Kind aplicado | Campos |
|---|---|---|
| `RACE_RESULT` | `RACE_RESULT_CORRECTED` | posição, grid, status |
| `SPRINT` | `RACE_SESSION_RESULT_CORRECTED` | posição, status, largada neutralizada, distância (%) — envia `eligibility` |
| `NUMBER` | `NUMBER_CORRECTED` | número (vazio ⇒ `null`, libera o número; regras #1/unicidade revalidadas no backend) |
| `STANDING` | `STANDING_CORRECTED` | pontos, vitórias, pódios, posição |
| `RACE` | `RACE_UPDATED` | nome, data, rodada, status |

Campos vazios não enviam a chave (mantêm o estado atual) — exceto `NUMBER`, cujo vazio significa `null`. `worldDate` = `defaultWorldDate`; `supersedesId` = `suggestedSupersedesId`; `raceId`/`driverProfileId`/`seasonId` vêm do próprio item do detalhe. O frontend **não** monta comandos fora desse conjunto — validação semântica final continua no backend.

## 4. Preview, confirmação e apply

- `Pré-visualizar correção` → `POST /api/timeline/corrections/preview` (motor real em transação com rollback; nunca persiste).
- A UI mostra **ANTES/DEPOIS** (`changes[]`), **IMPACTOS** (campeão antes/depois resolvido para nomes de piloto; `numberImpact.requiresAction` quando o `#1` exige reatribuição manual; `narrativeStaleEventIds`) e o aviso de que a fonte externa não é modificada.
- Aplicar exige dois passos: `Aplicar correção` → caixa de confirmação com o resumo contratual → `Aplicar correção` definitivo.
- `POST /api/timeline/corrections/apply` com `{ command, previewToken }`; sucesso mostra "Correção aplicada. O evento anterior foi preservado no histórico." e invalida `["timeline"]`, `["seasons"]`, `["races"]`.

### `409 PREVIEW_STALE`

Se o estado mudou entre preview e apply (outra correção concorrente), o backend rejeita com `PREVIEW_STALE` (sem escrita parcial). A UI:

1. descarta a pré-visualização antiga (`confirming` volta a `false`);
2. explica: "O estado do Universo mudou desde a pré-visualização. Gere uma nova pré-visualização antes de aplicar esta correção.";
3. oferece **Gerar nova pré-visualização**;
4. somente um novo preview habilita nova confirmação — o token antigo **nunca** é reutilizado.

---

## 5. Supersession e cadeia

- Aba **Histórico** mostra a cadeia completa (anteriores + atual + posteriores) com badge `Atual` no evento efetivo e `#sequence` nos demais.
- Exemplo canônico preservado: `77 → NUMBER_CORRECTED → 76 → NUMBER_CORRECTED → 77` — todos os eventos permanecem; a cadeia de correções é visível, nada é deletado ou sobrescrito.
- Evento substituído continua abrindo normalmente (somente leitura + edição permitida conforme edit model).

---

## 6. Regras derivadas e impacto

- Campeão e `#1` **não** são persistidos nem cascateados automaticamente (D-064/D-066): o preview explicita o impacto; a reatribuição de `#1` continua ação explícita do usuário.
- `points` de corrida/sprint permanece DERIVADO de `position/status` — o editor não oferece edição de pontos de resultado, apenas de standing (temporada sem resultados).
- Correções recomputam standings de forma determinística; a divergência com a fonte externa é leitura pura e não é "resolvida" automaticamente.
- A narrativa não é regenerada; a UI avisa quando há registros potencialmente desatualizados.

---

## 7. Segurança e isolamento

- Todas as chamadas passam pelas rotas autenticadas existentes (owner-only, 401/404 leak-safe). Nenhum privilégio novo; nenhum modo ADMIN.
- Isolamento por `universeId` garantido pelo motor (V3.15): alvo de outro universo retorna 404.
- External Mirror e universos de terceiros nunca são tocados; a UI repete esse contrato no preview.
- Nenhum endpoint destrutivo foi criado; não existe PATCH/DELETE de evento na timeline.

---

## 8. Concorrência

- Apply roda sob `pg_advisory_xact_lock('timeline:<universeId>')` com revalidação do token (V3.15).
- O editor assume pessimismo otimista: qualquer mudança concorrente invalida o token e força novo preview (`PREVIEW_STALE`).
- Duplo clique é mitigado por `isPending` nos botões de preview/apply.

## 11. Limitações e fora de escopo

- **Sem migration**: nenhum campo/tabela novo; o editor depende exclusivamente do modelo V3.15.
- **Fora de escopo (inalterado da V3.15):** troca de piloto/equipe em resultado, void/rollback de correção, branches, snapshot completo, regeneração narrativa, rerun de evolução, criação retroativa de resultado ausente, edição de `points` de corrida/sprint.
- **Sem formulários** para kinds informativos (`WORLD_ADVANCED`, `SESSION_COMPLETED`, `RACE_SCHEDULED`, `ATTRIBUTE_EVOLVED`) — `NO_VISUAL_EDITOR` com explicação na UI.
- **Evolução**: temporada com `ATTRIBUTE_EVOLVED` aplicado exige intervenção antes (`EVOLUTION_STALE`), como congelado na V3.15.
- **Narrativa**: avisos de stale apenas; nenhuma propagação automática.
