# V3.14 — Driver Persona / AI Character Profiles: Arquitetura (design-only)

> **Status:** especificação aprovada para implementação futura. Nenhum código, schema, migration, endpoint ou UI foi alterado nesta etapa.
> **Base auditada:** HEAD `f6de179` (branch `V3-NewFeats`). Todas as referências de código são do estado atual.

---

## 1. Executive Summary

A V3.14 introduz uma camada de **Persona** — como um personagem tende a falar, reagir e se comportar — separada de identidade, memória, relações, atributos esportivos e fatos externos.

Descobertas centrais da auditoria:

1. **Já existe um embrião**: `Character.dna` (Json) com contrato canônico em `dna-contract.ts` (chaves `personality, behavior, speechStyle, tendencies, values, traits`) e renderização no prompt como a seção opcional `CHARACTER_DNA`. Porém `dna` é **somente leitura no servidor**: nasce `{}` em toda criação (`characters.routes.ts`, `universe-init.service.ts`, `player-entry.service.ts`) e **nunca é editável** por API/UI.
2. `biography` (Character, ≤2000 chars, editável no CharacterForm) é o único campo de identidade narrativa realmente utilizável hoje; entra no prompt com cap de 600 chars.
3. O pipeline de geração tem ordem fixa de seções (`SECTION_IDS`), sendo `CHARACTER_DNA` uma das três opcionais (`{EXTERNAL_CONTEXT, CHARACTER_DNA, CURRENT_TURN}`) e renderizada **apenas para o speaker ativo**. `generationKey` deriva do `systemPrompt` (portanto reage a mudanças do speaker), mas **não** de `context.participants`.
4. AI Behavior (D-038/039) **não lê** `dna`/`biography`; decisões são heurísticas sobre temporada/corrida/conversa.
5. Não existe nenhum modelo de trait/confidence/evidence/source de persona. O mais próximo: `DriverAttribute` (esportivo, season-scoped), `Relationship.dimensions` (díade) e `Memory.source` (proveniência).
6. Personagens materializados de pilotos reais têm `userId = null` e `universeId` do Universe (**ownership por Universe**, não por `userId`); personagens originais têm `userId`; o catálogo AI oficial é global (`userId null`, `universeId null`) e read-only.

**Arquitetura recomendada (mínima):** Persona como modelo relacional próprio **1:1 com `Character`** (`CharacterPersona` + `PersonaTrait` + `PersonaEvidence`), com traits estruturados por chave canônica e confiança **por trait**; evidências relacionais com workflow `PROPOSED → APPROVED/REJECTED` que **nunca entram no prompt**; provisionamento **lazy** (sem dados inventados para pilotos reais); integração de geração **reutilizando o slot `CHARACTER_DNA`** (sem nova seção, sem renumeração, com fallback para `dna`/`biografia` legados); `dna` permanece intocado e marcado como deprecado; ownership segue a superfície existente (`userId` para originais, `universeId` para materializados); evolução futura passa exclusivamente pelo `persona.service` + auditoria na Timeline (sem segundo sistema temporal).

## 3. Domain Boundaries

```
EXTERNAL MIRROR          dados factuais de F1 (ExternalDriver/Team/Race…)
        ↓ materialização
UNIVERSE                 estado particular do usuário
        ↓
CHARACTER                identidade narrativa (nome, nacionalidade, gênero, nascimento, imagem, biography)
  ├─ DRIVERPROFILE       identidade esportiva (número, equipe, headshot custom)
  │    └─ DRIVERATTRIBUTE/TEAMPERFORMANCE   desempenho (simulação/evolução) — NUNCA persona
  ├─ PERSONA             tendências de fala/reação/comportamento (V3.14)
  ├─ MEMORY              o que aconteceu e foi lembrado (episódico)
  └─ RELATIONSHIP        estado díade-a-díade (afinidade/confiança/rivalidade)
        ↓
GENERATION CONTEXT       montagem efetiva do prompt (Persona ⇒ slot CHARACTER_DNA)
```

Princípios não negociáveis:

- Persona **não** substitui Memory nem Relationship.
- Persona **não** armazena fatos externos nem estatísticas.
- Persona **não** é um segundo `DriverAttribute`.
- Persona **não** vira histórico paralelo (Timeline continua sendo a infraestrutura temporal).
- `dna` atual permanece intocado (deprecado, sem remoção nesta fase).

## 4. Proposed Persona Model

### 4.1 Modelo relacional (novo, aditivo)

**`CharacterPersona`** (1:1 com Character):

| Campo | Tipo | Notas |
|---|---|---|
| `id` | uuid | PK |
| `characterId` | uuid **unique** | FK → Character (Cascade) |
| `origin` | enum `PersonaOrigin` = `ORIGINAL` \| `REAL_DRIVER` \| `AI_CHARACTER` | definido na criação (ver Provisioning) |
| `summary` | text? | retrato curto de voz/comportamento (≤2000, cap de prompt 600) |
| `schemaVersion` | text | ex.: `"persona.v1"` para evolução futura |
| `createdById` | uuid? | FK → User (auditoria de autoria) |
| `createdAt`/`updatedAt` | datetime | padrão do projeto |

**`PersonaTrait`** (N por persona):

| Campo | Tipo | Notas |
|---|---|---|
| `id` | uuid | PK |
| `personaId` | uuid | FK → CharacterPersona (Cascade) |
| `key` | text | chave canônica do registry (ex.: `humor`, `speechStyle`) |
| `value` | text | ≤200 chars |
| `confidence` | float | 0..1 (por trait — ver §7) |
| `sourceKind` | enum `PersonaTraitSource` = `MANUAL` \| `EVIDENCE` | como o valor foi definido |
| `evidenceId` | uuid? | FK → PersonaEvidence (SetNull) — evidência autoritativa quando `sourceKind = EVIDENCE` (D-055) |
| `createdAt`/`updatedAt` | datetime | |
| unique | `[personaId, key]` | 1 valor por chave |
| índice | `[personaId]` | leitura do speaker |
| índice | `[evidenceId]` | leitura da linhagem |

**`PersonaEvidence`** (N por persona, para pilotos reais e curadoria):

| Campo | Tipo | Notas |
|---|---|---|
| `id` | uuid | PK |
| `personaId` | uuid | FK → CharacterPersona (Cascade) |
| `traitKey` | text | chave sustentada (obrigatória — D-054) |
| `proposedValue` | text | valor proposto humanamente (≤200, obrigatório — D-054) |
| `sourceType` | enum `PersonaEvidenceType` = `OFFICIAL_PROFILE` \| `INTERVIEW` \| `BIOGRAPHY` \| `PUBLIC_STATEMENT` \| `OTHER_APPROVED` | sem scraping |
| `title` | text | ≤200 |
| `url` | text? | ≤2048, http(s) |
| `publishedAt` | datetime? | data da fonte |
| `excerpt` | text | ≤500 (resumo/trecho, nunca copy integral) |
| `confidence` | float | 0..1 (confiança da evidência) |
| `status` | enum `PersonaEvidenceStatus` = `PROPOSED` \| `APPROVED` \| `REJECTED` | nasce `PROPOSED` (default); só `APPROVED` conta |
| `createdById` | uuid? | FK → User (SetNull) |
| `reviewedById`/`reviewedAt` | uuid?/datetime? | auditoria de revisão ADMIN-only (D-057) |
| `createdAt`/`updatedAt` | datetime | |
| índices | `[personaId, status]`, `[personaId, traitKey]` | leitura de aprovação/pendências |

Regras do modelo:
- **Evidência nunca entra no prompt** (nada de trechos/URLs no systemPrompt): evidência justifica o trait na UI/auditoria e alimenta a confiança.
- **Confidence por trait** é o contrato do prompt (internamente); o valor nunca é mostrado ao modelo.
- **Evidência é proposta humana:** `traitKey` e `proposedValue` são obrigatórios; nenhum valor é derivado de `excerpt`, de LLM ou de heurística — a aprovação materializa o valor explicitamente proposto (D-054).
- **Autoridade entre evidências `APPROVED`** do mesmo `traitKey`: `confidence DESC → publishedAt DESC (NULLS LAST) → createdAt DESC → id ASC`; `PersonaTrait.evidenceId` aponta a autoritativa quando `sourceKind = EVIDENCE` (D-055). Ordem de aprovação não é critério.
- **Precedência de escrita:** `MANUAL > EVIDENCE` — editar um trait `EVIDENCE` converte para `MANUAL` (value manual, confidence `1.0`, `evidenceId = null`); aprovar evidência com trait `MANUAL` existente não altera o trait e a evidência permanece `APPROVED` (D-056).
- Sem `PersonaSnapshot`, sem tabela de histórico: mudanças futuras usam `TimelineEvent` (kind novo `PERSONA_UPDATED`, auditoria estado-neutra) — ver §18.
- Sem colunas especulativas por atributo: o registry de chaves evita "dezenas de campos".

### 4.2 Registry de traits (código, não banco)

Constante `PERSONA_TRAIT_REGISTRY` em `persona.rules.ts` (proposto), alinhada ao contrato existente e extensível por PR:

| Chave | Label | Prioridade (prompt) | Cap valor |
|---|---|---|---|
| `communicationStyle` | Estilo de comunicação | 1 | 200 |
| `speechStyle` | Maneira de falar | 2 | 200 |
| `humor` | Humor | 3 | 200 |
| `behavioralTendencies` | Tendências comportamentais | 4 | 200 |
| `emotionalExpression` | Expressão emocional | 5 | 200 |
| `competitiveness` | Competitividade | 6 | 200 |
| `confidence` | Autoconfiança | 7 | 200 |
| `interests` | Interesses | 8 | 200 |

Compatibilidade com o contrato atual: as chaves legadas `personality`, `behavior`, `tendencies`, `values`, `traits` continuam aceitas na **leitura** de `dna` legado (fallback); na Persona nova, valores livres dessas categorias devem ser mapeados para `behavioralTendencies`/`interests`. O normalizador legado (`dna-contract.ts`) permanece intocado.

## 5. Character / DriverProfile / SeasonDriverEntry / Persona Responsibilities

| Conceito | Responsabilidade | Campos | Quem edita |
|---|---|---|---|
| **Character** | Identidade narrativa estável | name, nationality, gender, birthDate, imageUrl, biography, controlledBy, userId, universeId; `dna` legado (deprecado, leitura no fallback) | Dono (via `/api/characters`) |
| **DriverProfile** | Identidade esportiva dentro do Universe | number (cache), teamId, customHeadshotUrl; relations para DriverAttribute/results/entries | Dono do Universe (via `/api/drivers`) |
| **SeasonDriverEntry** | Roster da temporada | seasonId, teamId, role, seat, number (autoridade do número, D-018), status | Roster service |
| **DriverAttribute / TeamPerformance** | Desempenho determinístico (simulação/evolução) | speed/consistency/racecraft/aggression; carSpeed/reliability/operations | Evolution engine (explícito) |
| **Persona** | Como fala, reage e se comporta (tendências) | summary, traits (key/value/confidence/sourceKind), evidence (proposed/approved) | Dono (originais) ou dono do Universe (pilotos materializados); evidência com curadoria |

Regra de ouro: **nada numérico de desempenho entra em Persona; nada comportamental entra em DriverAttribute.**

## 6. Persona Trait Model

- **Híbrido**: cabeçalho relacional (`CharacterPersona`) + traits em linhas (`PersonaTrait`). Não usar colunas fixas (rigidez) nem JSON opaco (sem confiança por trait, sem query, sem evidência relacional).
- Cada trait é 1 valor textual curto por chave; múltiplos interesses/tendências são expressos no texto do valor (ex.: `interests = "música, aviação histórica"`), sem arrays no v1.
- Chaves fora do registry são rejeitadas com `400 VALIDATION_ERROR` (evita lixo de prompt); o registry é a única fonte de labels/prioridades.
- Ordenação determinística do bloco: prioridade do registry → confiança desc → chave asc (nunca ordem incidental do banco).
- Cap de prompt: **máx. 12 traits**, **200 chars/valor**, **bloco total ≤ 2000 chars** (constantes espelhando os caps atuais de `dna-contract.ts`).

---

## 7. Confidence Model

- **Escopo**: confiança **por trait** (`PersonaTrait.confidence`) + confiança **por evidência** (`PersonaEvidence.confidence`). **Não** existe confiança global da persona (derivável; não duplicar).
- **Semântica**:
  - `sourceKind = MANUAL` → confiança default `1.0` (autoria do dono; pode ser ajustada se/quando a UI expuser o campo).
  - `sourceKind = EVIDENCE` → confiança do trait = confiança da evidência autoritativa (maior confiança entre as `APPROVED` do trait, desempate por D-055); `evidenceId` identifica a autoritativa. Sem evidência `APPROVED` restante, a autoridade deixa de existir (tratamento no reconcile — fase de service).
  - Trait proposto por evidência `PROPOSED` **não** é renderizado (fica fora do prompt até aprovação).
- **Prompt**: nunca envia números de confiança ao modelo; confiança serve para ordenar/cortar o bloco e para a UI.
- **UI**: exibe confiança como indicador qualitativo (alta/média/baixa) associado ao trait e à evidência; nunca como fato.

---

## 8. Sources & Evidence Model

- Estrutura da §4.1 (`PersonaEvidence`), com workflow `PROPOSED → APPROVED | REJECTED`, `APPROVED → REJECTED` e `REJECTED → APPROVED` (reexame).
- **Quem propõe**: dono do personagem no v1. **Quem aprova**: ADMIN-only no v1 (D-057), registrando `reviewedById`/`reviewedAt`; nenhum privilégio novo é criado além do papel ADMIN existente.
- **Fonte**: apenas URLs/refs aprovadas humanamente; **proibido scraping** e ingestão automática de mídia. `OTHER_APPROVED` cobre fontes que não se encaixam nas categorias, sempre com curadoria.
- Evidência é auditável (quem, quando, status) e nunca vira prompt.
- Distinção obrigatória no modelo: `FACT` (fato externo do Mirror — não é Persona) / `INTERPRETATION` (leitura humana — vira trait com confidence < 1.0 quando aplicável) / `PERSONA TRAIT` (valor renderizado) / `SOURCE EVIDENCE` (registro de suporte).

---

## 9. Original Character Model

- Personagem criado pelo usuário (`controlledBy USER`, `userId` definido) → `origin = ORIGINAL`.
- Persona **manual**: traits definidos pelo dono, `sourceKind = MANUAL`, sem evidência externa obrigatória.
- Totalmente editável pelo dono (mesmo ownership do Character: `character.userId === user.id`).
- Mesmo pipeline/slot de prompt dos pilotos reais (nenhum caminho especial em geração).
- Sem exigência de confidence explícita (default 1.0); o registry limita o vocabulário.

---

## 10. Real Driver Model

- Pilotos materializados do espelho (`ExternalBindingDriver`) → `origin = REAL_DRIVER` na primeira escrita de persona (detecção: existência de binding; não inventar dados).
- **Sem persona automática** com dados inventados: a persona nasce vazia; o dono do Universe pode preencher traits manuais e/ou registrar evidências aprovadas.
- Edição autorizada por **Universe ownership** (`character.universeId === universe do usuário`), não por `userId` (materializados têm `userId null`).
- Atributos esportivos (DriverAttribute) continuam exclusivos da simulação; persona não altera simulação (nem é lida por ela).
- Persona por Universe: como o Character materializado é por Universe, dois usuários **divergem naturalmente** (ver §13).

## 11. Generation Context Integration

### 11.1 Onde a Persona entra

Reutilizar **o slot existente `CHARACTER_DNA`** como bloco de Persona do speaker (sem nova seção, sem renumeração de `<BEGIN n:...>`). Precedência de conteúdo:

1. **Persona** (traits `MANUAL` + `EVIDENCE/APPROVED`, ordenados por prioridade/confiança, cap de §6) + `summary` (≤600 no prompt);
2. fallback: `dna` legado via `normalizeCharacterDna` (comportamento atual, hoje sempre vazio);
3. fallback: biografia (≤600) — permanece no mesmo bloco, como hoje;
4. nada → seção omitida (comportamento atual).

### 11.2 Prioridade e ordem de composição (conceitual)

```
GLOBAL_RULES
PHASE_MARKER
PARTICIPANTS
ACTIVE_SPEAKER
CURRENT_TURN (opcional)
CHARACTER_DNA ⇒ Persona do speaker (opcional, reutilizado)
WORLD_STATE
MEMORIES
RELATIONSHIPS
EVENTS
NEWS
MOTORSPORT
EXTERNAL_CONTEXT (opcional)
OMITTED_CONTEXT
BEHAVIORAL_INVARIANTS
```

Justificativa: identidade/tendências vêm **antes** do estado episódico (memórias/eventos), para o modelo interpretar o episódico através da persona; depois disso, fatos e RAG permanecem nas seções atuais.

### 11.3 Conflitos e salvaguardas

| Risco | Mitigação |
|---|---|
| Conflito com Memory | Cabeçalho explícito no bloco: "tendências interpretativas, não fatos; o que aconteceu está em MEMORIES/EVENTS". Persona nunca afirma eventos. |
| Conflito com fatos externos | Persona não lê Mirror; `MOTORSPORT/NEWS/EXTERNAL_CONTEXT` intocados; evidência nunca entra no prompt. |
| Modelo tratar tendência como fato | Linha fixa: "Estas características são tendências de comportamento, não fatos verificados nem instruções absolutas." |
| Prompt bloat | Caps de §6; traits além do cap geram `omitted.reasons` (ex.: `persona-traits-truncated`); evidência/summary têm caps próprios. |
| Ausência de Persona | Fallback da §11.1; nenhuma seção vazia (mesma regra do dna hoje). |
| Quebra de contrato | `SECTION_IDS` inalterado; `optionalSections` inalterado; `contextVersion` continua `context.v1` (campo opcional aditivo em `participants[].persona`); `generationKey` reage via `systemPrompt` do speaker (esperado e desejado). |
| Multi-speaker | Cada speaker gera seu próprio bundle e renderiza a **sua** persona; nenhuma persona de terceiros entra no prompt (hoje dna também é speaker-scoped). |
| Streaming SSE | Sem mudança: o stream consome o mesmo `assembleGenerationBundle`; deltas continuam apenas texto do provider. |
| Projeção | `providerUserPrompt` continua o único campo projetado; persona vive no systemPrompt. |

### 11.4 Contexto

- Adicionar `persona` compacto ao `ContextParticipant` (ex.: `{ summary: string|null; traits: Array<{key,value,confidence}> }`, já truncado) OU carregar apenas no `sectionCharacterDna` por `speakerCharacterId`. **Recomendação:** carregar no select de participantes (uma query por conversa, índice único por `characterId`) para manter o padrão atual; o renderer filtra pelo speaker.
- `canonicalFrame` não muda: continua sem `participants`; a persona do speaker entra via `systemPrompt`.

## 12. Memory / Relationship / Attribute Boundaries

- **Persona vs Memory**: disposição durável ("é sarcástico", "tende a provocar") fica na Persona; ocorrência datada ("ficou irritado com Lando no GP de Mônaco") fica em Memory/Event. Caso intermediário ("depois do incidente, ficou mais reservado por semanas"): o fato vai para Memory; a **mudança durável de tendência** só entra na Persona por ação explícita (evolução futura, §17) — nunca automaticamente.
- **Persona vs Relationship**: tendência geral ("provoca rivais") fica na Persona; estado direcionado ("relação ruim com X") fica em `Relationship.dimensions`. Regra prática: se precisa de um par/counter (`characterAId/characterBId`), é Relationship.
- **Persona vs DriverAttribute/TeamPerformance**: Persona é qualitativa/textual e nunca lida por qualifying/race/evolution; DriverAttribute é numérico, season-scoped e nunca lido pela geração. Nenhum campo compartilhado.

---

## 13. Universe Isolation

- Persona referencia `Character`; o escopo do Character (userId/universeId) define o escopo da persona — **sem coluna universeId redundante** (evita divergência de fonte).
- Materializados: `character.universeId` garante que Persona de A nunca é lida/editada por B (checagem de serviço + FK).
- Originais: `character.userId` garante ownership.
- Catálogo AI global (`universeId null`, `userId null`): persona **inexistente/read-only**; após `switch-control` (que re-aloja o Character no Universe), o dono passa a poder criar/editar a persona.
- Leituras de personagens de terceiros continuam `404` (não vazar existência), seguindo o padrão atual.

## 14. Provisioning

| Personagem | Persona no v1 |
|---|---|
| Original criado pelo usuário | **Lazy**: criada no primeiro `PATCH` (upsert); `GET` sintetiza persona vazia (`exists:false`) sem escrever |
| Piloto real materializado | **Lazy**; `origin = REAL_DRIVER` determinado no primeiro write pela existência de `ExternalBindingDriver`; **nunca** auto-preenchida |
| Personagem AI interno (switch-control) | Lazy após adoção (passa a ter `universeId`); origin = `AI_CHARACTER` |
| Catálogo AI global | Sem persona própria; read-only até adoção |
| Seed (`prisma/seed.ts`) | Sem mudança: `syncAiCatalog` continua sem persona |

- Lazy evita backfill em massa e linhas vazias; trade-off: um `upsert` no primeiro PATCH (idempotente, `P2002` tratado como no padrão do projeto).
- Nenhum dado de persona é criado a partir de idade/nacionalidade/nome (nada inventado).

## 15. API Proposal

Endpoints (nomes definitivos na implementação; contratos abaixo são o contrato esperado):

| Método | Rota | Descrição | Autorização |
|---|---|---|---|
| `GET` | `/api/characters/:characterId/persona` | View da persona (sintetiza vazia quando não existe) | Dono por `userId` **ou** por `universeId`; global = read-only vazia; terceiros = 404 |
| `PATCH` | `/api/characters/:characterId/persona` | Upsert: `summary?` e `traits?` (upsert de traits `MANUAL`; chave hoje `EVIDENCE` incluída converte para `MANUAL` — D-056); remoção nunca acontece por omissão | Dono por `userId`/`universeId`; global = 403 |
| `DELETE` | `/api/characters/:characterId/persona/traits/:key` | Remove trait (qualquer `sourceKind`); evidências permanecem; sem re-materialização automática | Dono por `userId`/`universeId`; global = 403 |
| `POST` | `/api/characters/:characterId/persona/evidence` | Cria evidência `PROPOSED` com `traitKey` + `proposedValue` obrigatórios (D-054) | Dono por `userId`/`universeId` |
| `PATCH` | `/api/persona-evidence/:evidenceId` | Muda status (`APPROVED`/`REJECTED`) e grava revisão | ADMIN-only no v1 (D-057) |

Schemas Zod (propostos):

```ts
const personaTraitSchema = z.object({
  key: z.enum(PERSONA_TRAIT_KEYS),
  value: z.string().trim().min(1).max(200),
  confidence: z.number().min(0).max(1).optional(),
});
const updatePersonaSchema = z.object({
  summary: z.string().trim().max(2000).nullable().optional(),
  traits: z.array(personaTraitSchema).max(24).optional(),
}).strict();
const createEvidenceSchema = z.object({
  traitKey: z.enum(PERSONA_TRAIT_KEYS),
  proposedValue: z.string().trim().min(1).max(200),
  sourceType: z.enum(PERSONA_EVIDENCE_TYPES),
  title: z.string().trim().min(1).max(200),
  url: z.string().url().max(2048).nullable().optional(),
  publishedAt: z.string().datetime({ offset: true }).nullable().optional(),
  excerpt: z.string().trim().min(1).max(500),
  confidence: z.number().min(0).max(1),
}).strict();
```

Erros: `400 VALIDATION_ERROR` (registry/caps), `403 FORBIDDEN` (catálogo global), `404 NOT_FOUND` (personagem/evidência inexistente ou de terceiros — leak-safe), `409 CONFLICT` (constraint única em corrida; padrão do projeto). Respostas nunca expõem evidência de terceiros nem campos internos; `GET` inclui `exists`, `origin`, `isRealDriver`, traits com confiança e evidências (apenas do próprio contexto autorizado).

## 16. UI Proposal

- **Originais**: seção "Persona" na página do Character (ao lado de "Sobre"), com editor de `summary` + traits (registry como selects + valor + confiança opcional); respeitar a regra "Characters: somente personagens do usuário" e a proibição já testada de despejar JSON cru.
- **Pilotos reais**: seção equivalente na página do Driver (read-only por padrão + edição quando o Universe é do usuário), com evidências listadas e status; sem editor manual de resultado/atributos.
- **Chat**: nenhuma mudança — persona não é seleção de personagem; continua backend-only no prompt.
- **Estados**: loading/erro/vazio/parcial (persona sem nenhum trait), badges de confiança (alta/média/baixa) e aviso "tendências, não fatos".
- **Não criar** página nova: estender detalhe do Character/Driver; sem redesenhos.

---

## 17. Future Evolution

- Persona pode evoluir (humor, agressividade, interesses, estilo) por **ação explícita** (usuário ou serviço de domínio futuro), sempre pelo `persona.service` (único writer).
- `schemaVersion` + registry permitem migração de formato sem quebrar geração.
- Sem mutação automática nesta fase: Evolution (V3.11 engine) e AI Behavior (D-038) **não** alteram persona; nenhum "Race finished → persona change" implícito.
- Histórico de mudanças: futuramente emitir `PERSONA_UPDATED` (TimelineEvent, estado-neutra) com payload mínimo `{ characterId, traitKeys, changedAt }` — sem guardar a persona inteira no evento (§18).
- Versionamento de persona (snapshot/versionamento pesado) fica **fora**; o modelo atual (linha + histórico na timeline) cobre auditoria.

---

## 18. Timeline Compatibility

- Persona **não** cria sistema temporal próprio; não há `PersonaSnapshot` nem entidade histórica paralela.
- Fronteira com V3.15 (Historical Timeline): revisões históricas/alternate history **não** reescrevem persona diretamente. Se uma mudança histórica exigir nova persona, ela será aplicada pelo `persona.service` como ação de domínio (com auditoria `PERSONA_UPDATED` na Timeline), nunca por replay implícito.
- Snapshots (`WorldSnapshot`) continuam armazenando world + standings; persona **não** entra em snapshots (é estado corrente do Character, não estado temporal reconstruído).

---

## 19. Performance

- Persona é carregada **apenas para o speaker ativo da geração** (bundle por speaker) — no máximo 1 query indexada extra por geração (`[personaId]`/`characterId` unique).
- Caps de §6 limitam tokens (bloco ≤2000 chars; summary ≤600 no prompt), mantendo o systemPrompt pequeno.
- Sem cache global; sem pré-carregar personas de todos os participantes (apenas o compacto do speaker; opcionalmente o resumo no select dos participantes).
- Multi-speaker: custo linear pelo número de speakers (≤3 hoje), cada um com sua própria persona; nenhuma persona de terceiros é carregada no prompt.
- Streaming SSE: nenhum custo adicional (mesmo bundle).
- AI Behavior: **não** lê persona no v1 (decisões permanecem heurísticas e determinísticas); habilitar futuramente exigiria novo contrato/decisão (OQ-4).

---

## 20. Migration Strategy

- **Novas tabelas**: `CharacterPersona`, `PersonaTrait`, `PersonaEvidence` + enums (`PersonaOrigin`, `PersonaTraitSource`, `PersonaEvidenceType`, `PersonaEvidenceStatus`). Aditiva, sem tocar dados existentes.
- **Relações alteradas**: nenhuma existente; novas relations em `Character` (`persona CharacterPersona?`) e em `User` (autoria/revisão: `createdPersonas`, `createdPersonaEvidence`, `reviewedPersonaEvidence`, todas SetNull).
- **Campos existentes**: `Character.dna` **permanece** (deprecado; leitura no fallback); `biography` permanece; `DriverAttribute/TeamPerformance` intocados.
- **Backfill**: nenhum (auditoria: `dna` é sempre `{}` em produção; sem dados a migrar).
- **Usuários/Characters/AI existentes**: funcionam sem persona (fallback); nada quebra.
- **Deleção**: FK `CharacterPersona.characterId` com Cascade; remoção de Character remove persona/traits/evidence.
- **Compatibilidade**: prompt/contrato inalterados sem persona; `contextVersion` estável; generationKey muda apenas quando persona existir (esperado).
- **Remoção de `dna`**: fica para uma fase de limpeza futura, após pelo menos uma versão de observação (documentado).

---

## 21. Testing Strategy (a implementar na fase de código)

- **Unit**: registry de traits (validação/caps/ordenação), confidence resolver (MANUAL/EVIDENCE/APPROVED), renderer do bloco (precedência persona → dna → biografia; omissão de seções vazias).
- **Service**: lazy upsert idempotente; replace de traits; `origin` correto (ORIGINAL/REAL_DRIVER/AI_CHARACTER); evidência PROPOSED não promove trait; concorrência (duas escritas → última vence sem duplicar linhas).
- **API**: contratos GET/PATCH/evidence (payloads, erros 400/403/404/409), ownership por `userId` e por `universeId`, catálogo global read-only.
- **Isolation**: Universes A/B com o mesmo piloto real divergem em persona; A não lê/edita persona de B; original de outro usuário → 404.
- **Persona variants**: inexistente (fallback), vazia, parcial (subset de traits), completa (cap), com traits > cap (truncamento + omitted reasons), com evidência pendente.
- **Prompt integration**: seção `CHARACTER_DNA` agora renderiza persona; multi-speaker (apenas a persona do speaker); generationKey muda com mudança do speaker e não com mudança de terceiro; contrato de seções opcionais preservado.
- **Streaming/AI Behavior/regressão**: SSE continua verde; AI Behavior não lê persona; suíte completa verde em banco limpo e reexecução (padrão V3.13).

## 22. Risks

| Risco | Severidade | Mitigação |
|---|---|---|
| Prompt tratar tendência como fato | Alta | Aviso explícito no bloco + testes de prompt; confiança/evidência nunca no prompt |
| Duplicação de conceito (`dna` × Persona) | Média | Persona substitui semanticamente; `dna` deprecado e usado só como fallback; coluna não removida |
| Vazamento de persona de outros universos | Alta | Ownership resolvido no serviço (userId/universeId), catálogo global read-only, testes de isolamento |
| Prompt bloat/limites imprevisíveis | Média | Caps fixos, ordenação determinística, `omitted` auditável |
| Evidência virar scraping/fatos não verificados | Alta | Sem ingestão automática; status PROPOSED/APPROVED; evidência fora do prompt |
| Quebra de contrato de geração | Média | Reuso do slot `CHARACTER_DNA` (sem novas seções), `contextVersion` estável, testes de contrato existentes preservados |
| Persona usada para gameplay (simulação) | Média | Proibição explícita + ausência de leitura nos engines; revisão de design |
| Evolução futura acoplar V3.14×V3.15 | Média | Fronteira §18; histórico via TimelineEvent, sem snapshot próprio |

## 23. Decisions

Registradas em `docs/v3-decisions.md` como **D-050..D-058** (novas):

- **D-050** — Persona é modelo próprio 1:1 com `Character` (sem `universeId` redundante), `dna` permanece deprecado como fallback e o prompt reutiliza o slot `CHARACTER_DNA` (sem nova seção).
- **D-051** — Traits estruturados (`PersonaTrait`) com confiança por trait e evidências relacionais com workflow `PROPOSED/APPROVED`; evidência nunca entra no prompt; sem scraping.
- **D-052** — Provisionamento lazy, sem persona inventada para pilotos reais; ownership por `userId` (originais) ou `universeId` (materializados); catálogo AI global read-only até adoção.
- **D-053** — Evolução futura exclusivamente via `persona.service` + auditoria `PERSONA_UPDATED` na Timeline; sem snapshot/versionamento paralelo e sem escrita automática por Evolution/AI Behavior.
- **D-054** — `PersonaEvidence` é proposta humana de trait (`traitKey`/`proposedValue` obrigatórios; nada derivado de `excerpt`/LLM); a aprovação materializa o valor proposto.
- **D-055** — `PersonaTrait.evidenceId` aponta a evidência autoritativa (`ON DELETE SET NULL`); autoridade por `confidence DESC → publishedAt DESC NULLS LAST → createdAt DESC → id ASC`.
- **D-056** — Precedência `MANUAL > EVIDENCE`, com conversão de trait `EVIDENCE` editado para `MANUAL` (confidence 1.0, `evidenceId` nulo) e sem sobrescrita silenciosa de trait manual.
- **D-057** — Auditoria de revisão (`reviewedById?`/`reviewedAt?`) e aprovação/rejeição ADMIN-only no v1.
- **D-058** — Sem evento `PERSONA_UPDATED` na Timeline neste corte; auditoria temporal de Persona fica para a fase de evolução.

Alternativas consideradas (ver §16 do pedido, sintetizadas):
- Persona no `DriverProfile` → rejeitada: Persona é comportamento do Character (não-pilotos também têm), e DriverProfile é esportivo.
- Persona só em `Character.dna` (JSON) → rejeitada como único storage: sem confiança por trait, sem evidência relacional/auditável, sem validação de escrita.
- Persona global por piloto real → rejeitada: não permite divergência entre universos (viola D-024/isolation), exigiria overrides complexos.
- `PersonaSource` + `PersonaTrait` + `PersonaEvidence` como três entidades separadas → simplificado para `CharacterPersona` + `PersonaTrait` + `PersonaEvidence` (a "source" é atributo da evidência, evitando tabela de fontes sem ganho).

---

## 24. Explicit Non-Goals

- Não implementar scraping nem ingestão automática de personalidade.
- Não usar LLM para inferir persona automaticamente nesta fase.
- Não alterar simulação, evolution engine, ai-behavior ou WorldState.
- Não criar endpoints/UI/migrations/schema nesta etapa (design-only).
- Não criar persona para todos os pilotos em massa nem dados inventados.
- Não criar segundo sistema temporal, branching ou alternate history.
- Não expor persona de terceiros; não tornar persona pública.
- Não alterar `dna`/`biography`/contrato de geração existentes.

---

## 25. Recommended Implementation Order

1. **Schema + migration aditiva** (`CharacterPersona`, `PersonaTrait`, `PersonaEvidence`, enums) + relações em `Character`/`User`; generate seguro (workflow Kiro `--no-engine`).
2. **`persona.rules.ts`** (registry, caps, confidence resolver) + testes unitários.
3. **`persona.service.ts`** (resolve access, lazy upsert, replace de traits, evidência) + testes de serviço/isolamento.
4. **Rotas + schemas Zod** (`GET/PATCH persona`, evidência) + testes de contrato/ownership.
5. **Integração de geração** (select de participantes + renderer no slot `CHARACTER_DNA` com fallback) + testes de prompt/multi-speaker/generationKey + suíte completa.
6. **UI mínima** (Character detail e Driver detail) + testes de integração/web.
7. **Docs/decisions finais** e commit por etapa (sem push/merge).

Cada etapa só inicia após a validação da anterior, com suíte API/Web verdes e DEV intocado.
