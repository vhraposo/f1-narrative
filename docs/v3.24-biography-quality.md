## 1. Trace ponta a ponta da biografia (estado V3.23)

```
GET /api/pilot-knowledge/drivers/:characterId            (pilot-knowledge.routes.ts)
 → ensurePilotKnowledgeProvisioned(characterId, now, { biographyComposer })   (provision.ts)
     ├─ coleta espelho (seasons → teams/championships, resultados → marcos)
     ├─ F1DB (dataset local): DOB, placeOfBirth, driverCode, stats, championshipYears
     ├─ biographyFacts (BiographyFacts)                          <- fatos normalizados em campos
     ├─ options.biographyComposer? {claims → LLM → sanitize}     <- V3.23: BIOGRAFIA LLM
     └─ upsertDriverProfileFromProvider(biographyContent | biographyFacts)
          └─ composeBiographyDisplay/Context (determinístico)   <- fallback/template
 → ExternalDriverProfile.biographyDisplay/biographyContext/biographySourceId  (persistência)
 → getDriverProfileView → GET → web (pilot-knowledge-panels.tsx) exibe display + origin
```

- **Provider LLM**: `GenerationProvider` existente (Ollama quando `OLLAMA_MODEL` definido; `nullProvider` caso contrário) injetado via `buildApp` → `pilotKnowledgeOptions.biographyProvider`.
- **Source ledger**: `ExternalKnowledgeSource` (provider/sourceKind/license/attribution/metadata).
- **Validação existente na V3.23**: apenas `sanitizeComposedBiography` — remove HTML/URLs/markdown, exige ≥80 chars, corta em 2400. **Nenhuma validação de idioma, cronologia, grounding em claims ou corrupção textual.**
- **Cache/regeneração**: bio `BIOGRAPHY_PAGE` era “provider-owned” e **nunca** era regenerada (regra de preservação da V3.23).

## 2. Evidência real (DEV, somente leitura)

`SELECT ... FROM ExternalDriverProfile` (2026-09-30) mostrou 5 biografias persistidas com `CURATED`/`BIOGRAPHY_PAGE` (LLM real, modelo local) e 1 determinística limpa (`DATABASE_EXPORT`, Albon).

Classes de defeito observadas, com trechos literais:

1. **Concatenação de palavras** — “demonstrou um **talentoexceptional** para o raciocínio rápido” (Max Verstappen).
2. **Mistura de idiomas** — “passando pelo kart, **followed por** carreiras de karts” (Bortoleto); “piloto iniciou sua carreira no **mundo do motor esportivo**” (Antonelli); “começou a se juntar ao **cartão de corrida de kart**” (Norris — tradução literal de “racing kart”); “começou a se **arrancar** pelas categorias” (Norris); “idade **precoç**” / “sua **estréia**” (Gasly — ortografia corrompida).
3. **Conteúdo especulativo/inventado** — “**talento inato**”, “conquistando **várias vitórias**” (Antonelli, sem claim), “caminho **contagiante**” (Bortoleto).
4. **Fatos externos não suportados pelos claims** — narrativas com kart/categorias sem nenhum claim correspondente no evidence bundle.
5. **Preservação do defeito** — como a fonte é `BIOGRAPHY_PAGE`, a regra “provider-owned preservado” impedia qualquer correção automática.

Ruled out (hipóteses descartadas com evidência):
- **Composer determinístico**: Albon (determinístico) está limpo; `composeBiographyDisplay` usa `joinList` com “ e ” e não concatena palavras.
- **Normalização de fonte**: DOB/local/nacionalidade corretos no perfil (`1997-09-30`, Hasselt, Dutch).
- **Tradução intermediária**: não existe etapa de tradução no pipeline.
- **Front-end**: a UI apenas renderiza `biography.display` (nenhuma interpolação).

## 3. Causas-raiz confirmadas

| # | Causa | Efeito |
| --- | --- | --- |
| C1 | **Persistência sem validação** (sanitize só de sintaxe) | Qualquer saída degradada do LLM vira biografia final |
| C2 | **Geração em texto livre sem contrato de claims** | Modelo completa lacunas com conhecimento próprio, mistura idiomas, inventa |
| C3 | **Guardrails apenas no prompt** | Modelos locais fracos ignoram parte das regras |
| C4 | **Sem verificação semântica** | Nenhuma checagem de suporte factual pós-geração |
| C5 | **Sem fallback degradável** | Falha de qualidade não tinha caminho alternativo |
| C6 | **Sem versionamento/fingerprint de regeneração** | Bio corrompida preservada para sempre |

## 4. Arquitetura corretiva (V3.24)

```
SOURCE (Jolpica/F1DB)
 → FACT (campos estruturados)
 → NORMALIZED FACT (claims tipados: id estável, valor canônico, human-readable, source, authority)
 → APPROVED CLAIM SET (filtro de autoridade/identidade; ordenado; deduplicado; fingerprint)
 → PLANNER (seleção + ordem narrativa; determinístico)
 → COMPOSER (1 chamada LLM, Structured Output estrito: sentences[{text, claimIds}])
 → QUALITY VALIDATOR (determinístico, genérico)
 → SEMANTIC VERIFIER (opcional, 1 chamada LLM, {approved, issues, unsupportedStatements, claimMismatches})
 → PERSISTENCE (somente se aprovado) | FALLBACK determinístico por templates de claims
```

- Identidade: claims só existem vinculados à identidade externa resolvida (F1DB id/abbreviation/nome completo); falha de ligação = claim não entra (`AMBIGUOUS_IDENTITY`).
- Autoridade: `STRUCTURED_CANONICAL` (F1DB/mirror) e `PRIMARY_OFFICIAL` entram; `SECONDARY` entra apenas se a arquitetura permitir; `UNVERIFIED` nunca entra.
- Regeneração: fingerprint dos claims + `generatorVersion` no metadata do ledger; bio `BIOGRAPHY_PAGE` é regenerada automaticamente quando a versão do composer muda ou quando o texto armazenado falha no quality validator (self-healing dos registros corrompidos do DEV).
- Observabilidade: metadata do ledger registra `generatorVersion`, `fingerprint`, `fallbackReason`, `model`, `claimsCount` — sem segredos e sem exposição na UI.

## 5. Implementação executada (status real)

### 5.1 Claims e normalização (D-089)
- `biography.claims.ts`: `ApprovedClaimSet` com IDs estáveis (`CLAIM-001…`), chaves tipadas (FULL_NAME, BIRTH_DATE, BIRTH_PLACE, NATIONALITY, F1_DEBUT, TEAM_SEASON por período contíguo, FIRST_WIN/PODIUM/POLE, CHAMPIONSHIP, CAREER_STATS, INTEREST), autoridade (`STRUCTURED_CANONICAL`/`SECONDARY`), fingerprint sha256 e ordenação cronológica determinística. `planBiographyClaimIds` ordena identidade → origem → carreira → conquistas → interesses.
- Identidade estrita (`resolveF1dbDriverStrict`): match exato por nome completo/nome curto/abbreviation; fallback sobrenome+inicial só quando há **um único** candidato — múltiplos = `AMBIGUOUS_IDENTITY` e o LLM é bloqueado (fallback determinístico).
- F1DB ampliado com `f1db-constructors.csv` + `f1db-seasons-entrants-drivers.csv` (test drivers excluídos) para timeline de equipes real (ex.: Max → Scuderia Toro Rosso 2015, Red Bull Racing 2016–2026), validado nos testes.

### 5.2 Composer v2 + validação (D-090)
- Contrato: `{"language":"pt-BR","sentences":[{"text","claimIds"}]}` com parse estrito (ids existentes, 2–12 frases, tamanho, idioma); cercas de código toleradas; nada de texto livre.
- `BiographyQualityValidator` genérico: HTML/markdown/URL/JSON/placeholder/caracteres de controle, contagem de frases, duplicação, **palavras concatenadas** (split de tokens longos contra o vocabulário), idioma misturado (function words EN), **substantivo próprio sem claim** (Ferrari/equipes inventadas), **ano sem claim** (cronologia), tokens longos desconhecidos com allowlist PT.
- `BiographySemanticVerifier` opcional (mesmo provider LLM): `{approved, issues, unsupportedStatements, claimMismatches}`; reprovação derruba para fallback; verifier indisponível não invalida texto já aprovado no quality validator.
- Fallback determinístico (compositor existente, claim-grounding via facts) com motivos observáveis: `ambiguous-identity`, `composer-unavailable`, `composer-error`, `composer-parse-failed`, `quality:<issue>`, `semantic:<issue>`.
- Self-healing: bio `BIOGRAPHY_PAGE` é regenerada quando `generatorVersion` muda ou quando o texto armazenado falha no validator re-construído com os claims atuais; bio de provider externo (F1DB/Wikidata) permanece preservada.
- Correções reais achadas na QA: plural "mundialis" → "títulos mundiais"; concordância "1 vitória/1 pódio/1 pole/1 volta mais rápida"; **líder de temporada em andamento não vira campeão** (títulos do espelho só entram se o F1DB tiver campeão final daquele ano).
